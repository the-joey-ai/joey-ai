# First run — the interview

The goal is not a complete document. It is a **started and specific** one. This file grows from every project afterwards, so treat first run as a conversation of six to ten exchanges, not an intake form — leaving with four sharp rules beats still answering questions about motion curves.

Ask one thing at a time.

## Before the first question

Check for existing design material. A design doc written for a past project is very often a de facto master that got tailored to one project — the durable half is already written, and the job is separating it from the project-specific half rather than starting cold. Joey has real candidates: the Joey browser's `docs/DESIGN.md` (the §11 personality contract is exactly signature material), Stork's `Context/DESIGN.md`, and the my-substack social-card system (locked palette, Lora serif, fixed geometry — taste, already made specific). Read what he points at first. That respects work already done, and it is a much better opening than a blank page.

## The arc

1. **"Which two or three apps or websites do you actually enjoy using?"** Enjoy *using*, not admire from a distance — the ones you reach for.

2. **For each one: what specifically?** This is the whole interview, and the first answer is almost always an adjective. Adjectives are not usable. Convert every one:

   | He says | You ask |
   |---|---|
   | "It's clean" | "What's missing that other apps have? Boxes? Borders? Colour?" |
   | "It feels calm" | "Does anything move when you tap? What happens when a page loads?" |
   | "The colours are nice" | "Which colour, and where does it appear? Is it on text, or on backgrounds?" |
   | "It's well organised" | "Are things in cards, or does the page just flow? What separates one part from the next?" |

   If you can open a site he names, open it and describe what you see, then ask whether that is the part he likes. Naming the actual thing — "the background is a warm off-white rather than pure white" — gets a truer answer than asking someone to introspect about design. If you can't open it, ask for one screen described in detail instead.

3. **"What do you screenshot or save when you see it?"** People save what they want to steal. This surfaces taste that can't be articulated.

4. **"What annoys you in the tools you use every day?"** The Don't column is easier to fill than the Do column, and it is just as load-bearing.

5. **"Anything you already know is yours?"** A colour, a font, a rule that's been applied without being written down. (The ivory + burnt-orange + Lora card system is a strong prior here — ask whether that's *the* signature or just the Substack's.)

## The read-back

Then read back what you heard, **as rules**, and let him correct it. The read-back is where vague answers become specific ones — someone who wouldn't volunteer "never pure white" will absolutely correct you when you say "so, white backgrounds."

## Then write the file

Follow the writing rules in `SKILL.md` — values not vibes, Execution notes empty unless real, the Do/Don't table as the product — and close by saying what happens next: the next project picks this file up automatically. That link is the reason the conversation was worth having.
